# Project Constraints

## Confirmed constraints

- Changes outside the user's explicit request or accepted proposal require approval before implementation. Migration work begins with the agent requesting any missing source instrument, target instrument, data/sample, cost, gap, and execution facts, then writing a reviewed migration-plan file. Presentation labels read source and target display names from that plan; candidate-filter rules remain deferred until separately approved.
- A completed migration delivery contains five items: the source-instrument main entry, source-instrument per-trade analysis, one combined cross-instrument ranking, target-instrument per-trade analysis, and a migration report. Source and cross-instrument entries link to each other in new tabs.
- Migration HTML publication is incremental. A new combined run declares `incremental_parent_run`; the fixed builder reuses every unchanged target per-trade chunk from that completed parent and generates chunks only for new candidates. It may rebuild the small ranking index, catalog, and summaries, but it must not regenerate unchanged candidate trade chunks.
- Final cumulative K200 publication is incremental when a compatible current snapshot exists. It reuses deterministic unchanged per-trade chunks and generates only missing coordinate chunks, while refreshing the cumulative ranking, catalog, summaries, and manifests. Reuse must not alter historical trade evidence or result metrics.
- Implementation and verification stay deliberately lean. Use the smallest code change that satisfies the confirmed contract; add defensive branches only for concrete severe risks. Avoid broad regression, repeated hash audits, and browser matrices unless changed semantics/data/results or an observed failure makes them necessary. Whenever work has a visible result and the environment allows it, provide one representative screenshot and judge basic overlap, garbling, asymmetry, and obvious layout errors. Computer Use may open local Chrome `file:///` pages.
- V4.4 lives in `D:\Code\backtest-release\Backtest V4.4`; V4.3 remains immutable historical evidence.
- V4.4 result bytes live physically under `F:\Backtest\Backtest V4.4\results`. The compatible logical path `D:\Code\backtest-release\Backtest V4.4\results` is a Windows directory junction to that F-drive root. Future result writers must preserve this mapping; source, plans, and project management remain on D.
- Completed evaluations use `results\evaluation_packages\<instrument_id>\<evaluation_start>__<evaluation_end>`. The timestamp slug includes seconds. Folder names never encode training, test, transfer, holdout, or descriptive roles.
- Every package records the exact instrument, interval, timezone, bar size, summary, candidate-set browser projections, immutable trade records, per-trade entry, provenance, and experiment note. Historical compatibility packages may hard-link immutable records and redirect their per-trade entry to a retained byte-preserved page.
- Every backtest plan binds one executable instrument profile and one exact evaluated interval. Any instrument and interval are allowed when data, preparation, cost, gap, low-activity, bar granularity, and campaign-mode requirements are complete.
- The generic comparison reader selects completed packages through `comparison_plan.json`, joins exact `combo_id` values, and never uses a directory name as an evidence role. Missing or duplicate comparison coordinates prevent complete status.
- Current stable K200 main/per-trade entries and the retained 350-coordinate comparison/per-trade pages remain byte-preserved. A package-backed replacement may become the stable target only after exact row/value parity, unchanged visible text, unchanged first-row data, equal rendered row count, and zero browser errors.
- `rolling_tr_sum` remains the sole baseline method. `all_window` is default; `exclude_marked` is optional and uses causal `baseline_available_from` timing.
- W candidates use every available prefix from 1 through W. No full-W or minimum-window-ratio gate applies; an early prefix maximum may govern the remainder of a position.
- The exact W candidate is `w_open_to_end_low_drop = open[start] - low[end]`, not an internal-high-to-later-low maximum ordered decline. Legacy raw audit names remain for compatibility.
- Pending entry is a retained signal under `fill_first_real_open`: it fills at the first real-trade bar open within 120 continuous candidate bars without trigger recross, higher-high cancellation, or structural-reversal cancellation.
- A rebound or speed signal on a non-real bar remains pending and fills at the next real-trade bar open inside the sample.
- Each future campaign binds an instrument cost reference. Notional equals frozen reference price times point value; commission, slippage, and any FX conversion determine that stage's round-trip bps. Raw compute keeps `entry_slippage=0`, raw fills, and raw returns unchanged. Existing K200 rows keep their historical cost reference and are not recomputed.
- Strategy semantics, instrument settings, and campaign intent are separate authorities. A new instrument cannot execute until the user confirms its cost model and gap policy.
- The four official modes are `transfer_exact`, `target_local_refinement`, `continuation_search`, and `fresh_search`. Exact transfer requires an exact freeze/plan coordinate-set match; local refinement requires a completed same-target transfer parent and machine-validated bounded neighborhood; continuation search requires a completed same-instrument, same-lineage parent; fresh search imports no source candidates or parent stage and binds the current exploration guide plus its legal search space.
- K200's authoritative execution granularity is 15 seconds. Every transfer target must use the same 15-second granularity, proven consistently by strategy contract, source and target profiles, preparation manifests, and observed data grids. Any mismatch stops and is reported to the user.
- Schema-v5+ `profile_optional` with no profile scenario set means no scenarios. K200 event fallback is restricted to explicit legacy execution.
- Gap and low-activity policies are supported, hash-bound executable identities. Profile declarations must match preparation-manifest policy/configuration/implementation identities; free-form `ready` labels are insufficient.
- Future entry qualification requires finite positive baseline, drop, and threshold values plus inclusive `drop >= threshold`. Historical raw and derived result files remain unchanged.
- Cumulative ranking uses the accepted V4.4 K200 major-version lineage as its partition. Minor V4.4 corrections remain beside existing rows in the same cumulative page. Engine, data-preparation, strategy, result-semantics, plan, and artifact hashes remain stage provenance and integrity evidence; they do not create a new ranking partition. A V4.5 major update creates a new K200 ranking lineage. Other instruments retain separate ranks and appear together only in a cross-instrument comparison.
- Every parameter-exploration agent must read and follow `project_management\05_domains\research\PARAMETER_EXPLORATION_GUIDE.en.md`. Improvement is a model-explained multi-metric judgment with no permanent high-weight metric and no fixed aggregate score.
- Parameter-search resolution must scale with parameter magnitude. E, BH, and S use relative multiplicative grids; continued single-digit absolute-step densification is treated as overfitting. Leap-search phases cover nonadjacent under-sampled regions, while grid phases refine only closed-evidence anchors.
- Exploration follows a repeating AI-led cycle: multi-round leap search, finite one-parameter grids around promising nonadjacent anchors, then renewed leap search. A round may be phase-specific. Each grid changes exactly one parameter while all other fields remain fixed; it has no fixed point-count cap, but finite bounds, step schedule, anchor, and expected coordinate count are frozen before compute. Interpret leap and grid evidence separately across the cycle.
- The user may correct goals, anchors, ranges, or direction between cycles. Autonomous work while the user is unavailable stays inside the explicitly authorized duration, instrument, method, data, and resource boundary.
- Mini KOSPI 200 tick facts remain provenance context only. The KRX contract multiplier is an active cost input.
- Fixed historical main/trade templates and the bound local Plotly asset are required for delivery.
- Every experiment needs a reviewed plan, isolated output, immutable raw closure, and an explicit evidence boundary. Intermediate rounds keep raw results and compact summaries only. Generate the cumulative main and shared per-trade HTML once after the exploration series ends, unless the user explicitly requests an intermediate publication.
- One executor or multiple executors may perform analysis, backtest compute, and HTML delivery. Delivery cannot begin from partial raw output.
- After Round N immutable closure, its HTML delivery and evidence analysis may run concurrently. Round N+1 planning, validation, and compute may overlap only with a closed current `SOURCE_FINAL`, exact plan/source identity and completed+active+pending anti-join, separate output roots and locks, a fresh memory/resource gate that includes the live delivery process, and exactly one cumulative HTML/union writer.
- `DELIVERY_FINAL` is required once for the final cumulative main and shared per-trade entries after the exploration series ends. A result-affecting source inconsistency discovered during that publication pauses further compute until a new source identity closes.
- Validation is risk-tiered. Version, engine, fill, return/cost, data, schema, execution-contract, and result-semantic changes require the complete regression suite. Frontend behavior changes require focused interaction checks. Presentation-only copy/style/layout changes require regenerated HTML, a simple functional check, and desktop/mobile screenshots; they do not require the complete suite unless behavior or data also changes.
- User-requested ZIPs contain current-version code, project management, analysis reports, the hash-bound 15-second OHLC, and transaction-record CSVs from every completed V4.4 stage. The sole compute-result exception is `batches/**/trades.csv` plus each completed stage's derived `analysis/stage_trades.csv`, copied under `trade_records/` with a hash-bound trade-record manifest. Other result payloads remain excluded.
- A formal source-release ZIP must preserve the project-relative source layout and include every repository module, template, plan definition, runtime input, dependency declaration, and local result fixture required by its packaged tests. It must expose one package-root test command and pass that command from an independent extraction. A compact UI-review ZIP may omit unrelated source/test dependencies only when it is labeled non-executable.
- Every exploration round ends with a standalone handoff directory containing expanded, unique next-round coordinates in `next_round_parameters.csv`. The CSV must pass an exact completed+active+pending anti-join before it can be bound into a reviewed execution plan.
- Before full target-data execution uses the generic transfer path, a small 15-second end-to-end smoke fixture must prove exact freeze/plan identity, target cost use, empty target scenarios, target-only lineage placement, target-name presentation, freeze-change invalidation, target-tuning rejection, and granularity enforcement.
